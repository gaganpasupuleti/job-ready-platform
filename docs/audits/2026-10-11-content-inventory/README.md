# Content inventory audit, 2026-10-11 (Astra M0 + F11)

This folder is the evidence package for the canonical content inventory. Every file
except this README is generated by a read-only tool from pinned git commits. The tool
does not connect to any database.

## Files

| File | Contents |
|---|---|
| `CONTENT_INVENTORY.md` | The nine counting-methodology counts per view, Sprint 1 adoption and version accounting, totals by source and category |
| `TOPIC_COVERAGE.md` | Coverage matrix for 40 repository topics in the six CRT and DSA areas, area totals, area-only batch questions, DSA concepts without a topic |
| `DUPLICATES_AND_GAPS.md` | Duplicate keys, cross-batch key reuse, exact and possible semantic duplicates, reference and seedability flags, coverage gaps |
| `EVIDENCE_AND_LIMITATIONS.md` | How the evidence was produced, manifest integrity, historical measurements, limitations |
| `SOURCE_COUNTS.json`, `SOURCE_COUNTS.csv` | Machine-readable counts |
| `CONTENT_ITEMS.json`, `CONTENT_ITEMS.csv` | One row per inventoried item, with source file, key, topic, difficulty, type, version, stem fingerprint, correct-answer count, explanation, related lesson, publication declaration, adoption mode, source branch and SHA |

## Reproduce

The four pinned commits must be in the clone. They are the current heads of these
remote branches:

```
git fetch origin master feature/visual-learning-phase1 feature/crt-dsa-content-sprint-1 content/sprint1-quality-gate
```

From `backend/`:

```
python -m app.content.inventory --out ../docs/audits/2026-10-11-content-inventory
python -m app.content.inventory --out ../docs/audits/2026-10-11-content-inventory --check
```

`--check` exits 1 if any committed file differs from a fresh generation. If a pinned
commit is missing, the tool exits 2 with `BLOCKED:` and the missing SHA. It does not
fall back to another branch. Attribute lookups use `git check-attr --source`, which
needs Git 2.40 or later.

Tests: `pytest tests/test_content_inventory.py`. Tests that need the pinned commits skip
with the missing SHA named when a shallow clone lacks them.

## Local seed check (disposable database, not production)

These results come from a disposable local Postgres database created for this audit at
master `bc4e80b`. They describe what the seed code does on an empty database. They are
not production counts. Production verification pending.

Steps: create an empty database, `python -m alembic upgrade head`, `python -m app.seed`,
count, `python -m app.seed` again, count, `python -m app.seed.phase11_activate`, count.
Counts were read with read-only queries.

| Step | Active questions | By domain | Placeholder rows | Coding problems |
|---|---:|---|---:|---:|
| After first `python -m app.seed` | 418 | ai 117, cloud 103, cybersecurity 80, devops 98, placement 10, technical 10 | 13 | 21 |
| After second `python -m app.seed` | 418 | unchanged | 13 | 21 |
| After `phase11_activate` (created 219, skipped 1) | 637 | ai 117, cloud 103, cybersecurity 80, devops 98, placement 119, technical 120 | 13 | 21 |

What this confirms from the source-level findings:

- Cloud receives none of the runner sample rows. The four rows flagged
  `topic-not-in-taxonomy` are skipped.
- 13 placeholder rows are inserted: 17 runner templates, less 3 with no taxonomy topic,
  less 1 whose topic an earlier runner row already filled.
- AI receives 117, not 118: one runner sample duplicates a build6 stem.
- `phase11_activate` creates 219 and skips 1, matching the 2026-09-05 production report.
  The skipped stem duplicates a runner grammar sample.
- After the first seed, 15 DSA paths are `COMING_SOON` as declared. After the second
  seed, all of them are `AVAILABLE`, including the 8 paths with no topic. Declared
  availability does not survive a re-seed.
- `python -m app.seed.runner` inserts nothing on an empty migrated database. Before this
  change it was cited in `README.md` (twice), `docs/DEVELOPMENT.md`, and
  `docs/PRACTICE_HUB.md`. They now say `python -m app.seed`.

The 2026-09-05 production report recorded 642 active MCQs. The local result is 637. The
difference is cloud +4 and technical +1. It is consistent with production having once
had the topics that the four cloud runner rows target, but this audit did not check
production. Production verification pending.
